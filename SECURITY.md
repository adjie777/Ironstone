# Security and privacy

This is a prototype running on synthetic data on a developer machine. It protects
no real person today. What follows separates what is **implemented and tested**
from what is **not done** — because a security document that blurs the two is
worse than none.

---

## Implemented and covered by tests

### Authentication

- Laravel Sanctum bearer tokens. Passwords hashed with bcrypt via the framework's
  `hashed` cast.
- Login is rate-limited (10/minute); AI endpoints 20/minute; general API
  120/minute.
- Inactive accounts are refused.
- **Failed logins are audited.** An audit trail that records only successes
  cannot show an attack.

### Authorisation — two independent gates

A clinical role permission is never sufficient on its own.

```
Gate 1  role permission        ApiController::requirePermission()  — fails closed
Gate 2  active consent         ConsentGate::allows()               — per data category
        ↓
        every passing read writes data_access_logs (visible to the citizen)
        every denial writes audit_logs with result = denied
```

Both gates live in the base controller, so a new endpoint cannot silently skip
them.

### The consent model

- Consent is **per data category**, not wholesale. A consent covering `timeline`
  does not open `laboratory`.
- Consent is checked **at read time**. Revocation takes effect on the next
  request — tested.
- A clinician's patient list is *derived from consent*. There is no global patient
  index to browse.
- Withheld categories are shown to the clinician as withheld, so a partial record
  is visibly partial rather than silently incomplete.

### Separation of population and individual data

Three mechanisms, each independent of the others:

1. Aggregate tables carry **no patient foreign key**. There is no join path from
   a government endpoint to an individual.
2. **No role holds both** `population.read` and any `patient.read.*` — asserted
   by a test over the seeded role matrix, so it cannot drift.
3. **Small-cell suppression.** Aggregate counts below the threshold return `null`
   with an explicit suppression flag, rather than being rounded. A count of one
   in a region is a person.

### Audit

Two separate trails, because they answer different questions and have different
retention needs:

| | `data_access_logs` | `audit_logs` |
|---|---|---|
| Audience | the citizen | the operator |
| Contains | who opened my record, when, which category, why, under which consent | every sensitive action including denials, logins, AI generation, status changes |

The citizen-facing log is generated by the system at the moment of access, not
written by the party doing the accessing.

### Data integrity and correction

- Every clinical record carries provenance: source system, source record id,
  recorded-at, verification status, confidence.
- A disputed record is **marked, not hidden**. A clinician may already have acted
  on it; making it disappear breaks the history instead of correcting it.
- Correction workflow: `submitted → under_review → verified → corrected | rejected`.

### AI safety

- The assistant answers only from records in the account and **refuses** rather
  than inferring — tested with an unanswerable question.
- Every AI response carries confidence, missing information, limitations and a
  not-a-diagnosis disclaimer. The safety envelope is applied in the abstract
  provider, so a subclass cannot omit it.
- The clinical summary reorganises existing records and explicitly proposes no
  diagnosis and no treatment.

### Input handling

- Form Requests validate at the boundary; `Rule::in` for every enumerated value.
- Eloquent parameter binding throughout; no raw SQL string interpolation.
- The SPA never renders server HTML, and no `dangerouslySetInnerHTML` is used.
- Secrets come from the environment. `.env` is not committed.

## Not done — do not deploy this

| Area | Status |
|---|---|
| Encryption at rest | Not implemented. No field-level encryption on clinical data. |
| Key management | None. No KMS, no rotation. |
| TLS | Not configured. Local HTTP only. |
| Penetration testing | Never performed. |
| Data-protection impact assessment | Not started. |
| Retention enforcement | Modelled conceptually; nothing expires or is purged. |
| Backup and restore | None. A restore has never been tested. |
| Session/token revocation at scale | Only per-user token deletion on logout. |
| MFA | Not implemented. |
| Secure hosting, WAF, DDoS | Out of scope. |
| Anonymisation for research consent | The flag exists; no anonymisation pipeline does. |
| Break-glass emergency access | Not implemented. The emergency profile is the citizen's own view only. |

**`SYSTEM_ADMIN` is a development-only role** and is labelled as such in the
seeder. It exists so the prototype can be operated locally. A role with those
rights should not exist in production; per spec §33, there is deliberately no
screen anywhere that lists all citizen records.

## Threats this design addresses

| Threat | Mitigation |
|---|---|
| Clinician browses records they have no relationship with | Patient list derived from consent; direct id access refused and the denial recorded |
| Government analyst re-identifies an individual | No patient key in aggregate tables; no role with both permissions; small cells suppressed |
| Citizen unaware their record was read | Access log written by the system, visible to them, including the authorising consent |
| Consent withdrawn but access continues | Consent evaluated at read time, not cached into a session |
| AI fabricates a medical record | Grounded provider with an explicit refusal path; tested |
| An alarming number shown without context | Risk always rendered with evidence, confidence, missing information and limits |
| Silent partial record | Withheld categories listed explicitly to the clinician |
| A composite "health score" driving decisions | No such column exists; a schema test enforces it |

## Threats it does not address

Anything requiring infrastructure: network interception, host compromise,
insider access to the database, credential stuffing at scale, supply-chain
compromise of dependencies. All of these are real and none is mitigated here.
